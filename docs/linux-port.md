# PicoView під Linux / Wayland — що це насправді означає

Коротка відповідь: це не налаштування і не прапорець компілятора, а другий
бекенд для всього, що програма робить, окрім власне логіки перегляду. Нижче —
чесний облік того, що доведеться написати, і план, за яким це робиться
поступово, не ламаючи версію для Windows.

**Стан на сьогодні: не зроблено.** Тут немає жодного рядка коду для Linux.
Цей файл — план, а не звіт.

## Чому це велика робота

Програма — 12 тисяч рядків, і швидкість, заради якої вона існує, тримається
саме на Windows-специфічних речах: `IMFMediaEngine` для відео, WIC для
картинок, кеш мініатюр Провідника, `D3D11CreateDevice` з прогрівом,
DirectComposition без redirection bitmap, `WM_NCCALCSIZE` для власної рамки.
Жодне з цього на Wayland не існує навіть приблизно.

| Підсистема | Зараз | Під Wayland | Обсяг |
|---|---|---|---|
| Вікно, рамка, ввід | Win32, `WM_NCCALCSIZE`, DWM | `xdg-shell` + `libdecor`, або SDL3 | великий |
| Композиція | DirectComposition + flip model | Vulkan/EGL, `wp_viewporter` | середній |
| 2D-малювання | Direct2D 1.1 | власний рендерер або Skia / NanoVG | **найбільший** |
| Текст | DirectWrite | HarfBuzz + FreeType + fontconfig | великий |
| Декодування | WIC + stb_image | libjpeg-turbo, libpng, libwebp, libheif, stb | середній |
| Відео та музика | Media Foundation | libmpv, або ffmpeg своїми руками | великий |
| Конвертація | Source Reader / Sink Writer | ffmpeg (libav*) | середній |
| Мініатюри | кеш Провідника | власний кеш на диску | малий |
| Прозорість/Mica | DWM | немає аналога; вирішити, що замість | дизайн |
| Асоціації | реєстр Windows | `.desktop` + MIME | малий |
| Додатки | `LoadLibrary`, `__try` | `dlopen`, і **SEH-захисту не буде** | малий |

Найдорожче — не відео і не декодери, а Direct2D і DirectWrite. Вони роблять
усе: заокруглені прямокутники, тіні, кліпи, розмиття, увесь текст, усі іконки.
`src/ui.cpp` — 3 665 рядків, і кожен його виклик малювання йде через них.

## План, який має сенс

Порядок важливий: кожен крок сам по собі корисний і перевіряється на Windows,
тож нічого не ламається наосліп.

**1. Відділити ядро від Windows.** Винести в код без `#include <windows.h>`:
розбір і запис налаштувань, сортування й фільтрацію списку файлів, таблиці
форматів, переклади, математику вирівнювання гучності, план генерованої
обкладинки. Це вже майже автономні шматки; головна робота — прибрати
`wstring` з інтерфейсів на користь UTF-8 `std::string`. Перевіряється тим, що
збірка під Windows далі проходить і старт не просів.

**2. Визначити межу платформи.** Один заголовок із тим, що бекенд мусить
уміти: створити вікно, дати поверхню для малювання, віддавати події,
намалювати прямокутник/текст/зображення, відкрити медіафайл. Windows-реалізація
— це нинішній код за цією межею.

**3. Малювання.** Тут рішення, від якого залежить усе інше:

- **Skia** — найближче до Direct2D за можливостями, малювання буде виглядати
  однаково. Ціна: +5–10 МБ до бінарника й важка збірка. Для програми, суть
  якої «один файл на 1 МБ», це майже відмова від ідеї.
- **Власний рендерер на Vulkan** — прямокутники зі скругленням і тінями через
  SDF у шейдері, текст через атлас гліфів. Це рівно те, що вже робить
  `src/blob.hlsl`, тільки для інтерфейсу. Кілька тижнів роботи, зате розмір
  лишається таким, як зараз.

Розумний вибір — другий, бо перший заперечує сенс програми.

**4. Текст.** HarfBuzz для шейпінгу, FreeType для растеризації, fontconfig
для пошуку шрифтів. Іконки Segoe Fluent доведеться замінити: їх немає й не
буде. Або власний набір SVG, або Material Symbols.

**5. Відео.** `libmpv` дає майже те саме, що `IMFMediaEngine`: відкрити,
грати, шукати, гучність, кадр у текстуру через render API. Це на порядок
менше роботи, ніж ffmpeg руками, і саме так варто починати.

**6. Пакування.** AppImage — найближче до нинішньої філософії: один файл,
який просто запускається.

## Скільки це

Реалістично — кілька місяців роботи однієї людини, з них більша половина на
пункт 3. Це окремий проєкт зі спільним ядром, а не гілка.

## Чого тут перевірити неможливо

На цій машині немає ні Linux, ні Wayland-композитора, тому будь-який код
звідси був би написаний наосліп і не запущений жодного разу. Тому його тут і
немає: план, який можна виконати, чесніший за півпорту, який не компілюється.

Перший крок, який можна зробити будь-коли й перевірити відразу, — пункт 1.
Він корисний і сам по собі: чисте ядро легше тестувати й на Windows.
